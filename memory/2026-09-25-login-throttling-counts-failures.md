# 两个在实测里才发现的登录问题

邮箱 + 密码登录（PRD §5.10）做完之后，用真实接口一步步量，撞到两个问题。两个都不是"代码写错了"，是"设计选错了"，代码评审看不出任何异常。

## 一、把成功的登录也算进了限流额度

第一版按邮箱 15 分钟 5 次，走 `RateLimiter.RateLimitKey(c, email)` —— 它内部是"查额度并扣掉"，**每个请求都扣**。实测「正确密码连登 6 次」：

```
第 1 次: 200
第 2 次: 429     ← 前面几次正确的登录把额度花完了
```

两个后果都很实：

- 一小时内登录五次的正常用户，被锁在自己的账号外面。
- 攻击者只要先烧掉额度，就能**故意**把本人锁出去 —— 拒绝服务是白送的。

对比之下，验证码那套从来只对**失败**计数（`email_codes.attempts`），密码这套没有理由不一样。所以把 `RateLimiter` 拆成：

```go
Allow(key) bool   // 只看，不扣
Hit(key)          // 失败时才扣
allow(key)        // 原有语义：查并扣（给"按请求计"的场景，比如发码）
```

修完实测：

```
正确密码连登 6 次      → 200 ×6
错 5 次                → 401 ×5，第 6 次 429
额度花光后用验证码登录  → 200      ← 找回的口子必须永远开着
```

## 二、响应时间在回答"这个邮箱注册过没有"

密码登录里，地址不存在就直接返回，存在则要走一次 bcrypt。第一次量：

```
已知邮箱 + 错密码: 0.0016s
不存在的邮箱:      0.181s
```

差 100 倍，等于一个"这个邮箱注册过没有"的查询接口。

修法是**不存在的地址也照样算一次哈希再丢掉**：

```go
case errors.Is(err, pgx.ErrNoRows):
    if _, hashErr := hashPassword(password); hashErr != nil {
        return nil, fmt.Errorf("failed to hash password: %w", hashErr)
    }
    return nil, ErrBadCredentials
```

比硬编码一个"假哈希"常量更省事（成本一样，都是一次 bcrypt），而且以后换哈希参数不会忘了同步那个常量。修完复量（两边额度都干净，各三轮）：

```
已知邮箱 + 错密码: 0.178s / 0.177s / 0.181s
不存在的邮箱:      0.180s / 0.179s / 0.179s
```

## 那个 0.0016s 是假的

第一次测出来的 1.6ms 不是"没有 bcrypt"，而是那个邮箱的**额度已经用光**、走的是 429 快路径 —— 量到的是另一条代码路径。**测侧信道之前先确认两条路走的是同一条路**，否则量到的是别的东西，还会得出相反的结论（那一刻的读数是"已知邮箱更快"，看起来像是安全的）。

## 下次

- 加任何"按账号"的限流，先问一句：**成功要不要花额度**？绝大多数场景答案是不。
- 新增一条认证路径，就问：**这条路的耗时和失败信息，能不能回答"这个账号存在吗"**？能，就补上等价的工作量。
