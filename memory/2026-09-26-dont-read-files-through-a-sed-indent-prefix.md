# 读文件不要顺手加缩进

为了输出好看，我常这么读文件：

```bash
cat src/foo.tsx | sed 's/^/  /'
```

然后在 `edit` 里把**带那两格缩进的文本**当作 `oldText` —— 文件里没有那两格，于是匹配失败：「Could not find edits[1]」。一次会话里因此白费了两次编辑（每次还得重新读一遍原文）。

规矩：**要看就原样读**（`read` 工具，或有行号有缩进但不加料的 `grep -n`）。要在终端里加缩进做展示，就别拿那段文本去改文件。

## 追加（同日）：同一个坑的第二张脸 —— 拿带缩进的输出当替换锚点

那篇讲的是「别把 `sed 's/^/  /'` 的输出当 `oldText`」，这次换成了 python 脚本里的字符串替换，
我又栽了三回：把 `awk`/`sed` 打印出来的**带前导空格的整段**直接抄进 `oldText`，
`s.count(old) == 1` 断言失败 —— 每次都白跑一轮。

规律：**任何把我看到的文本原样搬回去的动作都会中招**，因为「我看到」的文本已经被工具加了前缀。
两条防线：

1. 用**短、语义唯一的单行锚点**（如 `  const valid = dailyGoal >= 1 && dailyGoal <= 500`），
   不要抄整段多行块 —— 缩进层级越多，越容易错。
2. 真要动多行，先从文件里**程序化地打印行号与原文**（`awk 'NR>=a && NR<=b {printf "%d|%s\n", NR, $0}'`），
   按 `|` 后面的原始内容构造锚点。
3. 脚本里的每次替换都带 `assert s.count(old) == 1`，并且**先全部改完再写文件**（失败就不写，
   避免半改状态）。
